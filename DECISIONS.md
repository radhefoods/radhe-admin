# Decisions

Design and technical decisions of the Radhe Foods admin panel, with their reasons. Keep this file current. The conventions every page follows are in `CONTRIBUTING.md`.

## Decided at the start (2026-10-04)

The owner asked for a plan first and then the implementation, and for questions instead of assumptions. Nothing blocked the start, so these were decided and reported; any of them can be changed.

## Architecture

**Session.** Cookies travel with every call (`credentials: 'include'`). On `401 AUTH_TOKEN_INVALID` the refresh endpoint is asked once and the call is repeated; `AUTH_REFRESH_INVALID`, `AUTH_SESSION_REVOKED` and `ADMIN_ACCOUNT_DISABLED` end the session (`src/lib/api/session.ts`).

**Refreshes never run side by side.** Refresh tokens rotate, and a refresh that loses the rotation is answered with cleared cookies. Two tabs refreshing at once would therefore sign the admin out. Calls of one tab share one refresh; tabs of one browser take turns through the Web Locks API, and a tab that waited for another tab's refresh does not refresh again.

**A session that ends keeps the work.** When the session ends while the admin is working (12 hours without use, 72 hours in any case, a role change), the page stays as it is and a sign-in opens over it, with the email fixed. A half-filled form is still there afterwards. Signing in as someone else clears everything that was loaded.

**Forced password change.** `403 ADMIN_PASSWORD_CHANGE_REQUIRED` from any call, or `mustChangePassword` on the admin, routes to the change-password screen; nothing else renders until it is done.

**Permissions.** `can()` mirrors the API's rule exactly: `*`, `orders.*`, and `read` and `manage` independent. Navigation entries and pages need the read permission; buttons that change data stay visible, disabled, with a hint that names the missing permission. A `403 ADMIN_PERMISSION_DENIED` makes the panel ask the API again who the admin is, because the role may have been edited. The API enforces everything anyway.

**Status transitions come from the API.** The buttons of an order are exactly `allowedStatuses` (empty for a pending order: its payment confirms it); `canCancel`, `payment.needsRefund` and `refundable` decide the rest. The panel's own table of the documented transitions (`src/lib/status/transitions.ts`) only orders the steps (next, back, aside) and is checked against the documentation by a test.

**Money.** Integer cents end to end. Amounts are printed and read digit by digit (`src/lib/format/money.ts`); no float touches a price. Both ways of writing a decimal are understood (`19.99`, `19,99`, `1.234,56`).

**Time.** The API speaks UTC; the business thinks in German time. Every moment is printed in `Europe/Berlin` whatever the device is set to, and every typed time is read as German time and sent with its offset, across the changes to and from summer time (`src/lib/format/dates.ts`, tested for both nights).

**Errors.** `ApiError` carries the code, typed details and the request id. Each documented code has the panel's own sentence (`src/lib/api/error-text.ts`; a test checks that none is missing). An unexpected error also shows the API's message and the request id. A code the panel does not know (a newer API) is shown as a general error and kept in `rawCode`.

**Lists live in the address.** Filters, search, sort and page are query parameters, checked against what the API accepts before they are sent on. A filtered list can be bookmarked and survives the back button.

**Cursor lists have no total.** Customers, orders, returns, refunds, invoices, notifications, announcements and the stock history of a pack size are paged by cursor; the panel says how many rows it shows and offers "Load more". Products have pages and totals.

**Bulk actions work like the API.** The API takes the chosen orders (`orderIds`, up to 500) and answers every one of them with `changed` and a `reason`. The panel ticks orders in the list, sends their ids, and when any order was left as it is, shows every order with what happened to it; only when all of them changed does a toast with the count stand alone.

**Every refund is a decision in the panel.** The API never refunds by itself; it says that money waits (`payment.needsRefund`, `refundable.suggested`) after a cancellation or a credit note. The payment card of the order restates the suggested amount and opens the one refund dialog, through Stripe (only when `refundable.stripePossible`) or by hand; a manual refund is completed on the refund page once the money was sent. Stripe is named as the actor of what Stripe did.

**Confirmations.** Every destructive or money-moving action restates what will happen with the real numbers of the API before it runs: the paid amount before a cancellation, the count before and after a stock change, the suggested amount before a refund. The keyboard focus starts on "cancel" and Enter never confirms by accident.

**Optimistic updates only where a failure is harmless.** The switch that makes a product available answers at once and steps back if the API refuses. Nothing that moves money, stock or status is optimistic.

**Stock changes only through the stock endpoint.** The pack-size table shows the count of each pack size but never sends it: a `PATCH` with `stockQuantity` is refused by the API, and a count changed in a form would leave no line in the ledger. The opening stock of a new pack size is the one exception the API offers (`stockQuantity` in `variants[]` of `POST /products` and on `POST …/variants`), and the row takes it there; the API records it as a `restock` with the admin and the time.

**One product, one form, one save button.** The pack sizes of a product are rows of its form (the brief of 16 October 2026, section 5.5), not products of their own. A new product goes to the API in one request. An existing one has no single request: the API takes the product fields on `PATCH /products/{id}` and every pack size on an endpoint of its own. So the form sends a sequence, in this order: the product patch, the removed pack sizes, the changed ones, the added ones, each only when it differs from what the form was opened with. The sequence stops at the first refusal. What went through stays saved; the form is brought in line with the product as the API has it now, keeps the rows that were not saved as they were typed, says what was saved and what was not, and places the refusal at its row. Saving again sends only what is still different, so nothing is sent twice (the owner's rule of 16 October 2026). Removing a pack size is confirmed first; the last one cannot be removed, and one an order holds comes back from the API as `PRODUCT_VARIANT_IN_USE` with "disable it instead" as the way out. The duplicate endpoint is not used: pack sizes are managed in the table only (the owner, 16 October 2026).

**Unsaved changes.** A form that was changed asks before the tab closes or a link inside the panel is followed. The browser's back button is not intercepted: Next.js offers no supported way.

**Uploads.** `multipart/form-data` through `XMLHttpRequest`, because `fetch` cannot report upload progress, with the same session handling as every other call.

**Invoice PDFs** are fetched with the session and shown from a local blob: a plain link would not carry the session's refresh. The viewer offers "open in a new tab" and "download" as well, for phones and browsers that show no PDF inside a page.

**Admin names.** Records of the API carry an admin's id only. Names come from the team list, which needs `admin_users.read`; without it the panel shows the last characters of the id.

**Content security policy.** Every page gets a policy with a fresh nonce (`src/proxy.ts`): only the panel's own scripts run, and the browser only talks to the API. Inline styles are allowed because the positioning of menus and dialogs sets style attributes. The email preview of an announcement is shown in a frame that can run nothing.

**No search engine.** `noindex` in the metadata, in an `X-Robots-Tag` header and in `robots.txt`.

## What the API cannot do, and what the panel does instead

On 14 October 2026 the API answered the panel's requests (section 19 of `doc/ADMIN_API_DOCUMENTATION.md`): search and sorting on the lists with `GET …/count`, names next to ids, bulk actions on chosen orders, the progress of announcements in the list, `null` to clear optional texts, the integration flags in the settings, `deletable` on products, every refused file of an upload, the MFA reset command and the invitation email. On 16 October 2026 the API moved from pre-orders to a shop that sells from stock and is paid at checkout; the cargo rows of this table went with the cargos. The rows below are what remains.
