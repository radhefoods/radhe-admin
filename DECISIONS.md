# Decisions

Design and technical decisions of the Radhe Foods admin panel, with their reasons. Keep this file current. The conventions every page follows are in `CONTRIBUTING.md`.

## Decided at the start (2026-10-04)

The owner asked for a plan first and then the implementation, and for questions instead of assumptions. Nothing blocked the start, so these were decided and reported; any of them can be changed.

| Topic            | Decision                                                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Development data | The panel is developed and tested against a mock of the admin API (`mocks/`), as the owner decided for the shop: no development database exists and `radhe-api` is not run for now. |
| Design           | The family of the shop's approved system, tuned for dense work. Proposal: https://claude.ai/artifact/2ArpEGp7XxXACBB75rYcNT . Dark theme included, because tokens make it cheap.    |
| Git              | No commits unless asked.                                                                                                                                                            |
| Authority        | Where the concept documents and the API documentation differ, the API documentation wins. The source of `radhe-api` was read only to settle what the documentation leaves open.     |

## Architecture

**Session.** Cookies travel with every call (`credentials: 'include'`). On `401 AUTH_TOKEN_INVALID` the refresh endpoint is asked once and the call is repeated; `AUTH_REFRESH_INVALID`, `AUTH_SESSION_REVOKED` and `ADMIN_ACCOUNT_DISABLED` end the session (`src/lib/api/session.ts`).

**Refreshes never run side by side.** Refresh tokens rotate, and a refresh that loses the rotation is answered with cleared cookies. Two tabs refreshing at once would therefore sign the admin out. Calls of one tab share one refresh; tabs of one browser take turns through the Web Locks API, and a tab that waited for another tab's refresh does not refresh again.

**A session that ends keeps the work.** When the session ends while the admin is working (12 hours without use, 72 hours in any case, a role change), the page stays as it is and a sign-in opens over it, with the email fixed. A half-filled form is still there afterwards. Signing in as someone else clears everything that was loaded.

**Forced password change.** `403 ADMIN_PASSWORD_CHANGE_REQUIRED` from any call, or `mustChangePassword` on the admin, routes to the change-password screen; nothing else renders until it is done.

**Permissions.** `can()` mirrors the API's rule exactly: `*`, `orders.*`, and `read` and `manage` independent. Navigation entries and pages need the read permission; buttons that change data stay visible, disabled, with a hint that names the missing permission. A `403 ADMIN_PERMISSION_DENIED` makes the panel ask the API again who the admin is, because the role may have been edited. The API enforces everything anyway.

**Status transitions come from the API.** The buttons of an order are exactly `allowedStatuses` (empty for a pending order: its payment confirms it); `canCancel`, `payment.needsRefund` and `refundable` decide the rest. The panel's own table of the documented transitions (`src/lib/status/transitions.ts`) only orders the steps (next, back, aside) and is checked against the documentation by a test.

**Money.** Integer cents end to end. Amounts are printed and read digit by digit (`src/lib/format/money.ts`); no float touches a price. Both ways of writing a decimal are understood (`19.99`, `19,99`, `1.234,56`).

**Time.** The API speaks UTC; the business thinks in German time. Every moment is printed in `Europe/Berlin` whatever the device is set to, and every typed time is read as German time and sent with its offset, across the changes to and from summer time (`src/lib/format/dates.ts`, tested for both nights).

**Banners (19 October 2026).** The homepage banners (section 20, `doc/BANNERS.md`) are a page of the Catalogue group, `/catalogue/banners`, because they share the catalogue permissions and the people who tend the products tend the slides. One dialog serves both ways in: "New banner" takes the picture first, because the API creates a banner only from its file, and goes on with the form of the created banner, so that the admin names and links it without a second step; an existing banner opens with the same form. The form sends one `PATCH` with only the fields that changed, an emptied name as `""` and an emptied link or date as `null`, as the API documents. The start and the end are typed and shown as German time like every other moment of the panel (the brief says "the admin's local time"; the panel has one time for everyone, the business's), and go to the API as instants with their offset. The picture is checked in the browser before it is sent (wider than tall, at least 1200 × 300 px, JPEG/PNG/WebP, 10 MB), and the API's refusals have their own sentences, with the measured size. The order is sent as every id after a drop or a "Move up/down"; a `BANNER_ORDER_INVALID` answer reloads the list instead of restoring the stale order.

**Product order (24 October 2026).** A product has one position in its category (`sortOrder`, 0 first; `doc/PRODUCT_DISPLAY_ORDER.md`). The panel sets it on a page of its own per category, `/catalogue/categories/{id}/products`, reached from the row menu ("Product order"), rather than in a dialog: the list can be long and needs room for the handle, the typed place and the pack sizes. The page keeps a draft of the order and sends the whole list once, as the API answers it; a typed place moves the row and the field shows places from 1 while the API counts from 0. A `CATEGORY_PRODUCT_ORDER_INVALID` answer names the products that left the category and reloads the list instead of restoring the draft. The product form keeps the raw position as "Position in its category" (0 first, optional; a new product without it goes last) and points to the order page. The listing view of a category is a select on its form with the API's three values; the category sheet gained the `listing_view` column.

**Analytics (24 October 2026).** The start page became two tabs (`doc/ANALYTICS.md`): Decisions is the attention page as it was; Analytics shows the figures of a period. The tab and the period live in the address (`?tab=analytics&range=…&from=…&to=…&granularity=…`), so a reload and a shared link show the same figures; a custom range is not sent until both days are typed and in order, which is what the API would refuse with `ANALYTICS_RANGE_INVALID`. The charts are drawn by the panel itself as SVG (`src/components/data/charts.tsx`): the panel had no chart library, the dashboard needs four shapes (lines, bars, a donut, share bars), and drawing them with the theme's own tokens keeps the colours inside the system; every chart carries its numbers as a table for screen readers. The accent is the current period, the subtle ink the previous one, the danger dot the refunds. Each section is one endpoint and loads on its own; an answer is kept for a minute per period. `analytics.read` is a permission of its own in the role matrix, with an empty manage column.

**FAQ (24 October 2026).** The FAQ (`doc/FAQ.md`) is one page under a new Content group of the navigation, next to the blog, since both share the `content` permission; the legal texts stay under Settings so that nothing moves for the admins who know where they are. The page is the shop's order made editable: the groups are a sortable list of sections, every section holds a sortable list of its questions, and the questions without a group close the page. Both orders are saved the moment an entry is put down, the groups as the complete list and a group's questions as that group's complete list; `FAQ_ORDER_INVALID` and `FAQ_GROUP_ORDER_INVALID` leave the API's list standing instead of restoring the draft. The question form has one tab per language and a preview tab that renders the Markdown as the shop will; a problem in a language opens that language's tab. Publishing is the switch on the row and in the form (`PATCH isPublished`), and a group is deleted from its menu only once it is empty, as the API demands.

**Blog (24 October 2026).** The blog (`doc/BLOG.md`) is two pages: the posts, as the data table of the panel with the API's filters, sort and pages, and the categories, as a sortable list like the banners. A post is one form on a page of its own, like a product: the texts in two language tabs (title, address, summary, the Markdown text with a Write/Preview switch rendered by the renderer of the legal texts), and in the side column the publishing, the organisation (category, tags, author), the SEO fields and the pictures. The featured picture and the pictures for the text need the post's id, so a new post is saved as a draft first and gets its pictures on its page; a picture goes into the text at the cursor as `![description](address)` of the medium size. Publishing is a dialog with "Now" (the article is dated this moment) or "On a date" in German time: a future date schedules, a past date publishes with that date, and the same dialog changes the date of a published post; the panel does not let a post without its English text reach the publish button, and answers `BLOG_POST_INCOMPLETE` all the same. A taken address marks the slug field of the language that was typed. The form sends only what changed, and a slug only where it was retyped, since the API keeps the address otherwise.

**Wholesale quotations (25 October 2026).** The quotations (`doc/QUOTATIONS.md`, API section 24) are a group of their own in the navigation, "Wholesale", because they are a second channel with its own customers, not a kind of order. The list is the data table of the panel; the detail is one page with the lines as a small form: cartons and the net price per carton in euros, sent as cents, and only for the lines that changed. "Send quotation" is held back while prices are typed but not saved ("Save the prices first"), so what goes out is always what the API stored; it is also held back while a line has no price, and when the API still refuses with `QUOTATION_NOT_PRICED` the named lines are marked. Every action confirms in a dialog that restates the number, the company and the total, and the API's answer replaces the page at once. The PDF goes through the same viewer as the invoices (`src/components/domain/pdf-viewer.tsx`, fetched with the session, with a download and a way out to a new tab), since a plain link could not refresh the session. The emails about a quotation are listed on its page with a retry for a failed one, through the retry of the messages log. Closed quotations (accepted, declined, cancelled) show everything and change nothing. The permissions `quotations.read` and `quotations.manage` are a row of the roles matrix like any other; the demo order manager has both, the viewer reads.

**Wholesale catalogue (26 October 2026).** The wholesale site got a catalogue of its own in the API (`doc/WHOLESALE_CATALOG.md`, section 25): wholesale categories and wholesale products with SKUs, each a pack size in its carton with a stock in cartons and a ledger. The retail catalogue carries no cartons any more, so the "Packs per carton" field and the CSV column of the retail pack sizes went with it, and a quotation line names a wholesale SKU (`skuId`) and shows its stock. The pages live in the "Wholesale" group next to the quotations, at `/wholesale/products` and `/wholesale/categories`, with the same tables, forms, badges and dialogs as the retail catalogue: the product form saves in the same sequence as the retail one (the product, then each SKU to its own endpoint, stopping at the first refusal), the SKU table shows the carton the API works out rather than computing it, and a SKU set the API refuses (`WHOLESALE_SKU_INVALID`) is shown above the table. A category has a page of its own with its form, its picture and its products in order, because the brief describes them together; the retail tree keeps its dialog. Import and export reuse the retail dialog, which took the catalogue (endpoints, columns, permission) as a parameter; the picture manager and the category picture took the record's endpoints as a parameter for the same reason. Stock changes go only through the "Set stock" dialog (`PUT …/stock`, an exact count or a delta), below zero allowed as the API allows it, shown in red as a shortage; the ledger is a card on the product with a filter by SKU and pages. On a quotation, a short line is marked and a sent quotation with short lines carries a warning above its actions, but "Mark accepted" is never held back (the API refuses nothing for want of stock); an accepted quotation shows what was taken per line, before and after, and the list marks one that went short. The demo catalogue editor has `wholesale.read` and `wholesale.manage`, the viewer reads.

**Discount codes (27 October 2026).** The API got discount codes for the retail shop (`doc/DISCOUNT_CODES.md`, section 26): a code is a percentage or a fixed amount with an optional minimum, period, limit and once-per-customer rule; the customer applies it on the checkout page, the order reserves a use and the payment counts it. The pages live in the Catalogue group next to the banners, at `/catalogue/discounts`, with the same table, form, badges and dialogs as the rest: the list has the API's search and state filter and an on/off switch that sends `isActive` alone; a code has a page of its own with its form, its counts and the orders made with it, because the detail must show every field anyway and the wholesale category page set the pattern. The state comes from the API and is never worked out in the panel. The form holds text and converts on submit: a percent as a whole number, an amount in euros as cents, a German date and time as an instant; an emptied optional field goes as `null` on a change, and only what changed is sent. A code that orders used keeps its text (the field is disabled with the reason) and is switched off rather than deleted; if the API still refuses a delete with `DISCOUNT_IN_USE`, the dialog offers the switch. On an order, the code sits next to the number in the lists and the order shows its discount block, the share of each line and a Discount row between Goods and Delivery in both totals; a kept unit after a correction is paid at its unit price less its part of the line's discount, as the API computes it. Invoices and credit notes are the API's PDFs, so the panel renders nothing of theirs. The demo catalogue editor has `discounts.read` and `discounts.manage`, the viewer reads.

**Guests, closed accounts, referrals, reviews and problem reports (1 November 2026).** The API got guest orders, accounts that customers close, a referral programme, product reviews that the admin publishes, and problem reports after a delivery (`doc/CUSTOMER_ACCOUNTS.md`, sections 4, 9, 15 and 27 to 29 of the API documentation). One helper names a customer everywhere (`personName`, `personEmail`): a reference with `deleted: true`, or a customer with `status: "deleted"`, reads "Deleted account" with no email and no link to write to, on orders, returns, refunds, invoices, messages, reports, reviews, referrals, the start page and the search; the record itself keeps its page, since orders and documents still point at it, but shows nothing personal and no block button (the API answers `409 CUSTOMER_DELETED` anyway). The sign-up fields of before (`signupMethod`, `hasGoogleLogin`) left the panel with the API; `kind` took their place as a badge and a filter. Referrals live under Customers at `/referrals` as a list only, as the API offers them; reviews at `/reviews` with a page per review, where the answer is a small form of its own on the page rather than a dialog, because it is edited and replaced more often than decided; problem reports under Orders at `/issues` next to the returns, built on the return page: the same decisions by status, the refund resolution prefilled with the reported units and sent only when the admin changed them, and afterwards the notice that links to the payment of the order. A report is taken on before it is resolved or rejected, as the contract draws it; the API decides in the end, and a refused step reloads the report. The status filters of reports and reviews start on what waits (`open`, `pending`) and offer "All". The photos of a report open at full size in a dialog of their own, the panel's first picture viewer. The two windows of the return policy are one form, since the API saves them in one body. The demo order manager reads and moderates reviews, the viewer reads them; the permission count is 29.

**Order reviews (2 November 2026).** The API changed the reviews before they reached production: a customer reviews a delivered order as a whole, once, with stars and words (`doc/ORDER_REVIEWS.md`, section 28 of the API documentation); the product reviews and the order feedback of the day before are gone, and no product carries a rating. The panel follows without a new page: the review list shows the order, the customer, the stars, the clamped text, the author, the date and the status, and finds a review by the number of its order; the review page names the order and the customer and keeps its decisions. The order page lost the feedback card and shows the one review of the order instead, as a box with the stars, the words, the status and a link to the review, only for admins who may read reviews and only when a review exists. The rejection and deletion dialogs say what the contract now says: a review is written once, so the customer cannot rewrite it, and deleting it lets the customer review the order again.

**Points and rewards (2 November 2026).** The API got a loyalty program (`doc/REWARDS.md`, section 30 of the API documentation): coins for delivered orders, the sign-up, referrals and published reviews, redeemed at checkout for a percentage of the goods per coin, every rule set by the admin. The owner chose a group of its own in the sidebar rather than a place under Customers, since the coins are a programme of the shop and not a property of one customer; the Order manager and the Viewer read coins, and only the super admin changes the rules or adjusts by hand. The section is one page with four tabs in the address, Overview first because the numbers are what one opens the page for, then Settings, Accounts and Ledger; an account has a page of its own because it is linked from the ledger and the customer page. The rules are one form on the settings card, saved whole because the API replaces the document; the fields of a rule are disabled while its switch is off, an empty minimum or cap is sent as `null`, and the field names mirror the document so that a `VALIDATION_FAILED` answer lands on its field; `REWARDS_SETTINGS_INVALID` lands on the end of the campaign. The adjustment is a direction (add or take away) and a positive number, sent signed, with the reason the API records and a note; the dialog restates the balance before and after. Signed coins are green when they arrive and red when they leave, as the stock ledger colours its movements. The order page shows the coins next to the discount code with the same kind of block, the share per line under the line total, and a row in both totals blocks. The panel bounds the expiry at 1 to 120 months and the adjustment note at 500 characters, which the documentation leaves open.

**Audit before launch (5 November 2026).** The whole panel was reviewed for security, data integrity and stability; what was decided on the way:

- _Next.js 16.4.5._ 16.3.8 carried two unauthenticated remote code executions and a denial of service (fixed in 16.4.1); 16.4.5 is the security release of November, and 16.4.4 gives the shared Turbopack runtime the nonce this panel's policy needs, so the newest patch was taken rather than the first fixed one. `zod` went to 4.6.7 for its own advisory. What ships has no known vulnerability (`npm audit --omit=dev`).
- _The return address after the sign-in_ (`safeReturnTo`) is read the way a browser reads it and must stay on the panel's own origin: a tab or a line break in it (`/<tab>/evil.example`) would otherwise have led to another site right after a sign-in.
- _A path of the API is checked once, in the transport_ (`assertApiPath`): fixed text and ids, never `..`, an encoded character, a `?` or a `#`. An id comes from the address of the page, and a crafted address would have made the browser call another endpoint with the admin's session. A refused path reads as "not found".
- _A PDF is shown as a PDF_, whatever type the answer names (`pdfBlob`): the viewer is a frame of the panel's own origin.
- _A CSV export writes a cell that a spreadsheet would run as a formula as text_ (an apostrophe before `=`, `@`, and `+`/`-` unless the cell is only a number), and the import takes that apostrophe off again, so a round trip changes nothing. Excel files store text as text and need nothing. A sheet over 10 MB is refused before it is read.
- _Signing out is honest._ "Sign out everywhere" renews an expired access token like every other call (its path begins like the one of the plain sign-out, which needs none, and was matched with it), and a sign-out the API did not confirm leaves the panel signed in and says so. Before, the sign-in was shown while the cookies were still valid.
- _A page fails only when it has nothing to show_ (`pageFailed`): a refetch that fails while the page is open (the focus came back during a network drop) keeps the record and the form on it; `isError` alone used to replace both with an error. A record the API says is gone (404) still ends the page.
- _A form follows its record_ (`useFollowRecord`): when the record changes underneath, the fields nobody touched take the new value. The forms send "what differs from the record", so an untouched field that still held the older value was sent as a change and undid the other one (switch a discount code off in the header, edit its note, and it was on again).
- _The import runs only in the mode that was previewed._ The preview is kept with the choice about existing records it was made for; after a check that failed, nothing can be imported until one went through.
- _Refunds on the way._ `needsRefund` stays `true` until a refund is complete, while `suggested` already leaves out refunds that are decided. The payment card now says "a refund of X is on its way" instead of offering the rest of the payment as "waiting for a refund".
- _The amounts of a confirmation are the API's arithmetic_ (`src/features/orders/bill.ts`): a correction, a completed return and a refunded report restate what was paid for the units, so less their part of a discount code and of redeemed coins, not their list price.
- _Ticked orders are the ones on the page._ A tick does not outlive a change of the filters and reach an order the confirmation does not name; one action takes 500 orders, as the API does.
- _Every step of a quotation waits for unsaved prices_, not only "Send": the step runs on what the API stored and its answer replaces the page, so typed prices would be dropped, and accepting is final. This widens the rule of 25 October; say so if only "Send" should be held back.
- _A cursor list keeps its pages under its own key_ (`[..., "pages"]`): the order page read the returns of one order as a plain query under the same key as the returns list, and whichever came second crashed.
- _Navigation by code asks the unsaved-changes question too_ (`src/lib/unsaved.ts`): the search and a row of a table used to leave a half-filled form without a word. The search does not open over a dialog that waits for an answer.

The browser tests ran in full for the first time (52, desktop and phone, with the accessibility checks in both themes). Seven scripts written in October and never run were wrong, not the panel: selectors that matched two elements, a "back" fired before the page it should leave had opened, a chart hovered below the visible screen, and keys for a keyboard move sent without the gap a hand leaves (`moveWithKeys` in `e2e/support.ts` now paces them).

Not changed, on purpose: the Markdown renderer and the diff are still loaded with their pages (three rarely used content pages; loading them later would have meant rewriting tests that render them at once). The Excel reader and writer are loaded when a workbook is read or written, since four list pages carried them.

**Pictures per pack size (11 November 2026).** The API moved the pictures of a retail product to its pack sizes (`doc/VARIANT_IMAGES.md`, section 8): each pack size has a gallery of at most 8 with a main picture, the product itself has none, and the old paths `…/products/{id}/images…` answer `404`. The product page therefore has no picture card any more: the row of each pack size holds its gallery (the picture manager, with a counter "3 of 8"), which saves by itself and not with the form, because every picture call answers the whole product and replaces the product of the page. "Copy from another pack size" (shown when the product has more than one) lists the other pack sizes with their pictures to tick; a picture the pack size shows already (the same `url`) is ticked and locked, a file ticked under two pack sizes is sent once, and the panel always sends the ticked `imageIds`, never "all", so that it copies what the admin saw. A new product takes its pictures per row of the pack-size table: the files live in the form with their row, and after `POST /products` each row's files go to its pack size, found by its pack (the API answers the pack sizes smallest first), one request per pack size; a refused upload neither undoes the product nor stops the pictures of the other pack sizes. A pack size added to an existing product takes pictures once it is saved. The picture manager is still one component for both catalogues: its target (`ImageTarget`) says where the pictures are in the record and how many fit, `variantImages()` for a pack size (8) and, unchanged, `wholesaleImages()` for a wholesale product (12, `IMAGE_LIMITS`). Not built: a "copy this product" action; the retail panel never had one, so there was no picture option to reword (the API has `POST …/duplicate`).

**Order costs (11 November 2026).** The API works out what every order earned (`doc/ORDER_PROFIT.md`, section 32), with two permissions of its own, `finance.read` and `finance.manage`: buying prices and profit are not for everyone who works on orders. The panel knows them as the resource "Costs and profit" (33 permissions now), and asks none of the finance endpoints without `finance.read`. Settings → Order costs is a section of the shop settings next to "Delivery fee": delivery, packaging and other costs of one order in euros (sent as whole cents) and the estimate of the payment fee as a percentage and an amount, saved as the whole document; the example under the fields ("An order of €50.00 would cost …") follows what is typed and is an illustration of the two inputs, not a figure of an order. Because this section needs `finance.read` and the others `settings.read`, the settings area no longer asks for `settings.read` as a whole: each tab is shown with the permission of its section, the area opens for an admin who may open at least one, "Shop settings" in the sidebar likewise, and `/settings` leads to the first section the admin may open. A role with only `finance.read` sees the one tab, and `GET /settings` is not asked for it. The sentence "Product prices are calculated on the page Pricing & supplier" links to that page for a role that holds `catalog.read`, and the page links back.

**Cost & profit of an order (11 November 2026).** The order page has a section "Cost & profit" under the payment (`GET /finance/orders/{id}/profit`, `doc/ORDER_PROFIT.md`): the notes on what kind of figures these are, a table of the products as the order ended with the ordered figure crossed out next to one that changed, a row that opens to the calculation of one pack, the order summary, what refunds changed, and what the customer paid. Without `finance.read` there is no section and the endpoint is not asked. The breakdown is a query of the order (`orders.profit`), so everything that loads the order again (a correction, a return, a cancellation, a refund, a status change) loads it again without a rule of its own. **The panel adds no figures up**: every total is the API's, because adding rounded figures gives other totals. The one exception is the row "Cost after fulfilment" of the one-pack calculation, which the documentation defines as `cost + fulfilment + extra` and the API does not name; it is formed from the unrounded steps. Amounts print with two decimals in the tables and with up to four decimals of a euro in the calculation of one pack (€0.1435, and €1.38 where that is exact); costs print as negative amounts, the net profit green or red by its sign. The mock API works the breakdown out with the API's own rules (`order-profit.ts`, ported); what a real order carries from the day it was placed (buying prices, the price rule, the costs of an order, Stripe's fee) the demo orders do not have, so the mock derives them from the article and order numbers: every fifth article has a price set by hand, every ninth no buying price, every sixth order is from before the costs were kept, and Stripe has reported the fee of every second paid order.

**Price rule and buying prices (11 November 2026).** Steps 2 and 3 of `doc/ADMIN_PANEL_SUPPLY_PRICING_IMAGES_AGENT_PROMPT.md` (`doc/SUPPLIER_IMPORT.md`, section 31). A selling price is the buying price, plus the fulfilment cost on it, plus other expenses, plus the markup on all of that, plus the VAT of the product; the API calculates every price that counts. _Settings → Pricing & supplier_ (`/settings/pricing`, shown with `catalog.read`, saved with `catalog.manage`) holds the rule of the shop, the safety buffer, the check before activation and the brand list. The rule and the brand list are two cards with a save of their own: the card of the rule sends `safetyUnits`, `pricing` and `publishCheck` and leaves `brands` out, so the list stays; the card of the list sends the list with the rule and the buffer **as they are saved**, which the API wants every time and which recalculates nothing. A changed value of the rule is confirmed first (every calculated price of the shop changes at once), and the answer's `repriced` is said afterwards. Two rows for one prefix (compared as the import compares them: case, accents and punctuation do not matter) are refused in the panel, because the API would merge them silently and the last would win. _On a pack size_: a buying price (euros with up to six decimals, since the API keeps four decimals of a cent) and the switch "Price follows the buying price" (`priceMode`). While it is on, the regular price is shown and cannot be typed, and the form **never sends a regular price** for such a pack size: the API would take a price without a mode as the admin's and make the pack size `manual`. A new pack size needs a regular price even in `auto` (the API keeps it, then calculates over it), so the form fills in what the rule gives; while the rule is not known, or without a buying price, the price is typed. What the form shows before a save ("about €2.19") is the panel's own calculation of the same rule (`src/features/supply/pricing.ts`); what counts is the API's answer. _On the product page_: a block "Pricing" from `GET /supply/products/{id}/pricing`, one pack size at a time (the calculation with who sets each value, what customers pay, the profit as a markup and as a margin, a warning for a price below cost, the supplier's line), and under it the values of the rule the product sets itself. _In the category dialog_: the same four optional fields and the switch "Goods that are not food". An override is sent as a whole with only the values that are set, and `null` when none is, as the API replaces it as a whole; under an empty field stands the value that counts instead and who sets it, resolved in the panel from the shop's rule and the categories (the breakdown of the API only says who sets the value that wins). The pricing of a product is a query of the product (`products.pricing`), so every save of the product loads it again. The mock API recalculates as the API does (`mocks/pricing.ts`, a port of `cost-pricing.ts`); the demo has buying prices on all products but one, and three spices whose price follows the buying price. Not built yet: steps 4 to 7 (the check before activation, the upload of the supplier's file, the review list, merging).

**A price rule per pack size (11 November 2026).** `doc/ADMIN_PANEL_SKU_PRICE_RULE_AGENT_PROMPT.md` (documentation, section 31, "A rule per pack size"). The API prices a pack size by four levels, value by value: the pack size itself (`priceRule`), its product, the category, the shop. The guide puts a small form into the "Pricing" block; **the owner chose the other way: the four optional fields stand in every pack-size row of the product form** and are saved with the row, so a rule can be typed while a product is created. A row sends `priceRule` with only the values that are set, in `POST /products`, `POST …/variants` and `PATCH …/variants/{variantId}`; a `PATCH` sends it only when a value changed, then as a whole (the API replaces what the pack size had), and `null` when the pack size keeps none. Under an empty field stands what the pack size follows and who sets it (the rule of the product as the form stands: the shop, the chosen category, the product's own values). "Follow the product" empties the four fields of a row; the removal is sent with the save, like every change of a row. The price a row shows before a save ("about €25.17") and the price a new pack size in `auto` is sent with are calculated with the row's own values first. A regular price is still never sent for a pack size in `auto`, with or without a rule. For a pack size priced by hand the row says that its rule changes only the profit shown. A pack size that has a rule carries the badge "Own price rule" in its row and in the "Pricing" block; the block reads `rule` and `sources` of the pack size that is chosen (no longer those of the product) and names "this pack size" as a source. The form "Price rule of this product" stays as it was. On a pack size, `pricing` is the price and `priceRule` the rule; on a product and a category, `pricing` is the rule. The mock API resolves the four levels in the recalculation and in the pricing answer; the demo's 10 kg Basmati Rice has a rule of its own (12 % and 40 %, priced by hand). The panel must go live after the API: an API without the change refuses `priceRule` with `400 VALIDATION_FAILED`.

**Six legal pages (11 November 2026).** `doc/LEGAL_PAGES.md`, `doc/ADMIN_PANEL_LEGAL_PAGES_AGENT_PROMPT.md` (documentation, section 6). Settings → Legal texts manages six pages instead of two: imprint, shipping information, refund policy, terms, privacy policy, right of withdrawal, in the order the API answers them. The screens there were are extended, nothing stands next to them: the overview is six sections, each built from `GET …/pages` (what is published and by whom, the draft, the links) with the version table under it from `GET /legal-documents` as before. Only the terms and the privacy policy carry the badge "Accepted at checkout" and can raise the red checkout warning (`requiredTypes`); a page that only informs and is not published says "Not shown in the shop yet", never anything about the checkout, and the sentences about customers accepting a version are said for those two only. **The links are built the way the website routes its legal pages**, read in `radhe-web/src/i18n/routing.ts` on the owner's instruction: `{shop}/en/legal/{address}` and `{shop}/de/rechtliches/{address}`, the shop being `NEXT_PUBLIC_SHOP_URL`. A link is clickable once the page has a published version; before that the address is shown as text, since the page does not exist for customers. The address and the search-engine texts of a page are a dialog per section ("Page settings"), saved with `PUT …/pages/{type}` as the whole page: an empty field is left out and means the default, which the field shows as its placeholder (`defaultSlug`, the title of the current version); an address that equals the default is shown as an empty field. "Back to the defaults" empties the fields and is sent with the save. `LEGAL_SLUG_TAKEN` is shown at the address field of the language that was refused, with the label of the page that has the address. The rule that English is required to publish is gone: a version is published with its text in one language, and the editor, the preview and the publish confirmation say that readers of the other language will see that text. The history and the page of a version name who published and who created it. The mock API has the six types, both pages calls, the taken-address rule of the API and the relaxed publish rule; its demo texts are placeholders (imprint published, shipping as a draft, refund published in German only, no right of withdrawal yet).

**Errors.** `ApiError` carries the code, typed details and the request id. Each documented code has the panel's own sentence (`src/lib/api/error-text.ts`; a test checks that none is missing). An unexpected error also shows the API's message and the request id. A code the panel does not know (a newer API) is shown as a general error and kept in `rawCode`.

**Lists live in the address.** Filters, search, sort and page are query parameters, checked against what the API accepts before they are sent on. A filtered list can be bookmarked and survives the back button.

**Cursor lists have no total.** Customers, orders, returns, refunds, invoices, notifications, announcements and the stock history of a pack size are paged by cursor; the panel says how many rows it shows and offers "Load more". Products have pages and totals.

**Bulk actions work like the API.** The API takes the chosen orders (`orderIds`, up to 500) and answers every one of them with `changed` and a `reason`. The panel ticks orders in the list, sends their ids, and when any order was left as it is, shows every order with what happened to it; only when all of them changed does a toast with the count stand alone.

**Every refund is a decision in the panel.** The API never refunds by itself; it says that money waits (`payment.needsRefund`, `refundable.suggested`) after a cancellation or a credit note. The payment card of the order restates the suggested amount and opens the one refund dialog, through Stripe (only when `refundable.stripePossible`) or by hand; a manual refund is completed on the refund page once the money was sent. Stripe is named as the actor of what Stripe did.

**Confirmations.** Every destructive or money-moving action restates what will happen with the real numbers of the API before it runs: the paid amount before a cancellation, the count before and after a stock change, the suggested amount before a refund. The keyboard focus starts on "cancel" and Enter never confirms by accident.

**Optimistic updates only where a failure is harmless.** The switch that makes a product available answers at once and steps back if the API refuses. Nothing that moves money, stock or status is optimistic.

**Stock changes only through the stock endpoint.** The pack-size table shows the count of each pack size but never sends it: a `PATCH` with `stockQuantity` is refused by the API, and a count changed in a form would leave no line in the ledger. The opening stock of a new pack size is the one exception the API offers (`stockQuantity` in `variants[]` of `POST /products` and on `POST …/variants`), and the row takes it there; the API records it as a `restock` with the admin and the time.

**One product, one form, one save button.** The pack sizes of a product are rows of its form (the brief of 16 October 2026, section 5.5), not products of their own. A new product goes to the API in one request. An existing one has no single request: the API takes the product fields on `PATCH /products/{id}` and every pack size on an endpoint of its own. So the form sends a sequence, in this order: the product patch, the removed pack sizes, the changed ones, the added ones, each only when it differs from what the form was opened with. The sequence stops at the first refusal. What went through stays saved; the form is brought in line with the product as the API has it now, keeps the rows that were not saved as they were typed, says what was saved and what was not, and places the refusal at its row. Saving again sends only what is still different, so nothing is sent twice (the owner's rule of 16 October 2026). Removing a pack size is confirmed first; the last one cannot be removed, and one an order holds comes back from the API as `PRODUCT_VARIANT_IN_USE` with "disable it instead" as the way out. The duplicate endpoint is not used: pack sizes are managed in the table only (the owner, 16 October 2026).

**Unsaved changes.** A form that was changed asks before the tab closes or a link inside the panel is followed. The browser's back button is not intercepted: Next.js offers no supported way.

**Uploads.** `multipart/form-data` through `XMLHttpRequest`, because `fetch` cannot report upload progress, with the same session handling as every other call.

**Invoice PDFs** are fetched with the session and shown from a local blob: a plain link would not carry the session's refresh. The viewer offers "open in a new tab" and "download" as well, for phones and browsers that show no PDF inside a page.

**Admin names.** Records of the API carry an admin's id only. Names come from the team list, which needs `admin_users.read`; without it the panel shows the last characters of the id.

**Content security policy.** Every page gets a policy with a fresh nonce (`src/proxy.ts`): only the panel's own scripts run, and the browser only talks to the API. Inline styles are allowed because the positioning of menus and dialogs sets style attributes. The email preview of an announcement is shown in a frame that can run nothing.

**No search engine.** `noindex` in the metadata, in an `X-Robots-Tag` header and in `robots.txt`.
